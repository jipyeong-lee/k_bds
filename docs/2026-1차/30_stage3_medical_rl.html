Stage-3 · 의료 RL (RaR 루브릭 보상)

개방형 의료 VQA(medix)는 정답의 표현이 여러 가지다. 그래서 문자열 일치로 검증할 수 없다. 대신 Rubric-as-a-Reward(arXiv:2507.17746)를 쓴다. 심판이 가중 다기준 체크리스트를 항목별 0/1 로 채점한다. 보상은 가중 평균이다: r = Σwⱼcⱼ / Σwⱼ ∈ [0,1]. 부분점수가 생기므로 보상은 0 과 1 사이의 값이 된다.

루브릭 구성 (configs/medical_reward.py build_rubric)

의도: medix 는 단답 멀티모달 문항이다. 루브릭은 정답 여부와 함께 "이미지를 보고 근거를 대며 맞혔는가"를 항목별로 채점한다.

RaR 루브릭 표. 가중치는 RaR 정수 스킴(Essential 5 / Important 3 / Pitfall 4)이다.

키 (#)항목 (한/영)유형(가중)대상판정 기준(요지)
c1 (1)정답 정확성 / Answer correctnessEssential 5<answer><answer> 가 참조답과 의미가 같다(동의어·단위 환산·환언 허용). 참조답을 기준 문장에 넣는다(템플릿 주입)
c2 (2)시각적 근거 / Visual groundingImportant 3<think><think> 가 이미지와 모순 없는 관찰을 쓰고 답을 뒷받침한다(교차 추론). 없는 구조·소견을 지어내면 0 이다
c3 (3)정밀도·단위 / Numeric precision & unitImportant 3<answer>수치는 참조답의 ±15% 이내이고 단위는 참조답과 같다. 측정형 문제에만 자동으로 넣는다(참조답이 숫자+단위 정규식에 맞을 때)
c4 (4)환각·과잉주장 없음 / No hallucination / overclaimPitfall 4전체이미지에 없는 소견과 질문 범위 밖의 주장을 추가하지 않는다(기준 문장은 긍정형으로 쓴다)

집계: r = Σwⱼ·cⱼ / Σwⱼ ∈ [0,1]. 실제 비중:

  • 비측정형(분모 12): c1 42% · c2 25% · c4 33%.
  • 측정형(분모 15): c1 33% · c2 20% · c3 20% · c4 27%.
  • 정답성(c1)의 비중이 가장 크다. 환각 억제(c4)가 다음이다.

설계 결정:

  • 정적 통일 루브릭: 문제마다 루브릭을 만들지 않는다. medix 40건에서 정적 루브릭과 인스턴스식(논문 방식)을 비교했다. 정적 루브릭이 오답 기각(오답 응답 점수, 낮을수록 좋음: 0.000 대 0.118)과 환각 변별(클수록 좋음: +0.338 대 +0.021)에서 나았다. 인스턴스식은 이미지 없이 텍스트만으로 루브릭을 만든다. 그래서 시각 근거 항목을 만들지 못한다. 그러므로 정적 루브릭을 채택했다.
  • 참조답 템플릿 주입: 단답이므로 채점할 사실은 참조답 1개다. c1 기준에 참조답을 넣는다. 참조답만 넣으면 되므로 코드가 루브릭을 만든다. 오프라인 LLM 생성 단계가 없다(비용 0, 매번 같은 루브릭).
  • 측정형 자동 분기(is_measurement): 정답에 의료 단위(mm/cm/HU/° 등)가 있으면 c3 를 넣는다. 판정식은 참조답의 \d+\s*(mm|cm|...) 정규식이다. 정규식에 맞지 않으면 c3 를 뺀다(예: "X-ray" 문항은 c1·c2·c4).
  • 형식 게이트(format_ok): <think> 에 실질 추론(≥15자, 형식 점수 format_think 의 16자와 다르다)과 <answer> 가 있어야 심판을 부른다. 형식을 어기면 심판을 부르지 않고 0.0 을 준다(비용 절감, 보상 해킹 방지).
  • c2 완화 이력: 초판 "실제 소견 인용"("구체적이 아니면 0")은 너무 엄격했다. 점수가 항상 0 이었다. 기준을 "이미지(영상)와 모순 없는 관찰"로 완화했다. 완화 후 c2 점수도 응답에 따라 0 과 1 로 갈렸다. 분포 프로브에서 c2 는 정답 응답 0.94 대 환각 응답 0.00 이다(2부 §8-결과).
  • 데이터: medix 는 단답 VQA 다(정답 중앙값 47자, 모달리티 태그 포함, 51,335건 실측, 예 "28×27mm"·"28 x 27 mm"·"X-ray"). RaR-Medicine-20k(텍스트 전용·장문, 9~12항목 인스턴스 루브릭)는 쓰지 않는다. 스키마만 빌린다: {"title","description":"<Category> Criteria: ...","weight":정수}.

심판 출력 형식은 2부 §4.2 에 있다.

구현과 심판

  • configs/medical_reward.py ClinicalJudgeReward(AsyncORM): 처리 순서는 형식 게이트, 멀티모달 심판 호출(env JUDGE_BASE_URL/MODEL/API_KEY), JSON 0/1 파싱, 집계다. 타임아웃과 파싱 실패는 0.0 이다.
  • 사용법: 
    --reward_funcs format_think clinical_judge --external_plugins configs/accuracy.py configs/medical_reward.py --reward_weights 0.2 1.0
  • 심판은 KHDP deepseek-v4-1-flash-ax 다(2026-10-15~). JUDGE_API_KEY=$KHDP_PAT 를 pod env 로 넘긴다. KISTI 계산 노드에 외부망이 없어서 kgpu 에서 실행한다(../CLAUDE.md §2.5).

검증

  • 통과한 검증(옛 KISTI 내부 심판 Qwen3.6-27B-FP8 기준): 유닛테스트 29/29, 심판 스모크(FP8 모델이 40GB GPU 1장에 적재됨, 정답 1.0 > 오답 0.0), KISTI 내부망 도달성, 분포 프로브(2부 §8-결과).
  • GRPO 배선 end-to-end 스모크(35_stage3_smoke.slurm)를 통과했다. 플러그인 로드, clinical_judge 해석, kwargs 전달, 보상 합산을 확인했다. 현재 심판(KHDP)으로는 kgpu Stage-3 스모크를 통과했다(2026-10-15, ../CLAUDE.md §2.5).
    • 버그 1건을 고쳤다. swift 는 images 를 str 경로가 아니라 dict {bytes,path} 로 넘긴다. _image_to_data_url 이 str/dict/PIL 을 모두 받도록 고쳤다. 고치지 않으면 심판이 이미지를 보지 못해 c2 를 채점하지 못한다. 재검증을 통과했다(data_url_ok=True, clinical_judge 0.58→1.0, reward = 0.2·Format + 1.0·Clinical).
  • RL 알고리즘: RaR 은 보상 설계다. 최적화는 GRPO 계열이다. Stage-3 에는 scale_rewards=gdpo(GDPO)를 권고한다. 심판 보상(가중치 1.0)과 형식 보상(가중치 0.2)은 분포가 다른 다중 보상이다. GDPO 는 이런 다중 보상을 위한 방법이다. Stage-2 A/B 에서 GDPO 는 성능을 낮추지 않았다(판정). dr_grpo 코어(loss_type=dr_grpo · dynamic_sample)는 그대로 쓴다.

남은 것

Stage-3 는 전문가 3종 통합 모델에서 시작한다. Stage-3 본 학습은 2차 과제로 넘겼다(00_overview.html §3).

목표 벤치마크: HealthBench

Stage-2 holdout(세 도메인 1,772건)은 검증 가능한 정답 기준의 내부 지표다. 최종 의료 능력은 외부 의료 벤치마크 HealthBench(OpenAI, 2025-05, 의사 262명 · 대화 5,000건 · 루브릭 채점)로 잰다. 파이프라인(SFT, RLVR, RaR)의 각 단계 모델을 같은 평가 도구로 잰다. 그 결과로 기본 모델 대비 개선을 추적한다.

측정 설정(scripts/45_healthbench_smoke.slurm + run_healthbench.py, evalscope health_bench):

  • 평가 문항은 Hard 부분집합 전체 1,000건이다(변별력이 가장 높은 부분집합). max_tokens 는 8,192 다.
  • 채점자는 자체 Qwen3.6-27B-FP8(thinking off)이다. 오프라인 클러스터라 GPT-4.1 을 쓸 수 없다. 데이터는 로컬 캐시(오프라인)다.
  • HB_TARGET_MODEL env 로 평가 대상을 바꾼다. 기본 모델, 콜드스타트, Stage-2·3 모델을 같은 조건으로 비교한다.

해석 주의.
  1. 채점자가 GPT-4.1 이 아니다. 그래서 공식 리더보드와 직접 비교할 수 없다(내부 비교 전용).
  2. 채점자 파싱 실패를 보수적으로 처리한다. 그래서 점수는 하한으로 읽는다.
  3. 기본 모델은 응답이 길다(최대 44K자). max_tokens 가 일부 답을 잘랐다.
추적 계획: SFT 모델(v3), 통합 모델, Stage-3(RaR) 모델을 같은 평가 도구로 잰다. 결과로 위 표의 빈 행을 채운다.

2부. Stage-3 의료 복합 보상 (clinical_judge) 구현 스펙

절 번호는 원 스펙의 번호를 그대로 쓴다. 원 스펙의 §3·5·6·7·9 는 1부에 흡수하고 삭제했다.
대상: configs/medical_reward.py + scripts/30_medical_rl.slurm
상태: 구현·검증 완료(보상, 심판 Qwen3.6-27B-FP8 분포 프로브 통과). 배선은 35_stage3_smoke.slurm 로 확인했다(1부 검증).

1. 목표 & 범위

  • 심판은 Stage-3(개방형 의료 RL)에서만 쓴다. Stage-2 RLVR 은 심판을 쓰지 않는다. Stage-2 는 검증 가능한 정답을 accuracy_mix(configs/accuracy.py)로 규칙 채점한다(RLVR 의 정의). accuracy_mix 는 <answer> 안의 답을 먼저 꺼낸다. 수식 정답은 math_verify 로 비교한다. 객관식 문자와 짧은 문자열은 정규화 일치로 비교한다. \boxed{} 는 답 정규화와 태그가 없을 때의 대체 추출에만 쓴다.
  • Stage-3 데이터 MBZUAI/medix-rl-data(자유형식 임상 QA, solution = 참조답)는 정답의 표현이 여러 가지다. 그래서 문자열 일치나 규칙 채점을 할 수 없다. 대신 LLM 심판(LLM-as-judge)이 임상 유효성을 평가한다.
  • 복합 보상은 형식(규칙)과 임상 유효성(심판)을 합친다. 계획서는 보상 해킹·환각 억제와 다각도 평가를 요구한다.
  • medix 일부 답(측정값 등)은 거의 검증 가능하다. 그 부분집합에는 accuracy 를 함께 쓸 수 있다(선택). 구현은 이 대안 대신 심판의 c3 항목을 쓴다.

2. 결정: AsyncORM 으로 외부 멀티모달 심판 API 호출

심판은 대형 멀티모달 모델을 API 로 쓸 예정이었다. 그래서 학습 프로세스 안에 심판을 적재하는 방식은 맞지 않았다.

  • ms-swift 네이티브 GenRMPlugin 은 심판 모델을 TransformersEngine 으로 학습 프로세스 안에 적재한다. 이 방식은 외부 API 와 맞지 않는다. 이 방식은 학습 GPU 를 점유한다. 그래서 쓰지 않는다.
  • 대신 AsyncORM 을 상속한다. GRPO 트레이너는 async ORM 을 asyncio.gather 로 병렬 호출한다. 트레이너는 images/solution 등 데이터셋 컬럼을 reward_kwargs 로 넘긴다. 심판 API 를 async 로 호출하므로 학습 GPU 를 점유하지 않는다. 사용법은 1부 구현과 심판에 있다.

4. clinical_judge 상세 (ClinicalJudgeReward(AsyncORM)): 멀티모달 API 심판

파일: configs/medical_reward.py. 파일 끝에서 orms['clinical_judge'] = ClinicalJudgeReward 로 등록한다.

4.1 동작

  • async __call__(self, completions, **kwargs): kwargs 에서 solution(참조답), images(이미지), messages(질문)를 꺼낸다.
  • completion 마다 멀티모달 심판 API 를 호출한다(이미지, 질문, 참조답, 모델 답변). 응답에서 항목별 0/1 JSON 을 파싱해 가중 집계한다. 호출은 asyncio.gather 로 병렬 처리한다.
  • 클라이언트: AsyncOpenAI(base_url=$JUDGE_BASE_URL, api_key=$JUDGE_API_KEY), model=$JUDGE_MODEL. 이미지는 OpenAI 멀티모달 포맷(image_url base64)으로 보낸다. swift 는 실제로 이미지를 dict {bytes,path} 로 넘긴다. 그래서 _image_to_data_url 을 고쳤다(1부 검증).

4.2 루브릭 = Rubric-as-a-Reward(RaR, arXiv:2507.17746) 방식 (확정)

판정을 단일 스칼라 대신 가중 다기준 체크리스트(0/1)로 나눈다(집계식은 1부). 부분점수는 그룹 안 보상의 분산이 0 이 되는 문제(zero-std)를 줄인다(Stage-2 교훈).

데이터 실측, 루브릭 생성 생략, RaR-Medicine-20k 스키마 차용은 1부 루브릭 구성 · 설계 결정에 있다.

정적 4차원 루브릭은 1부 RaR 루브릭 표에 있다.

  • 심판 출력은 파싱 가능한 JSON 이다. 
    {"c1":0/1,"c2":0/1,"c3":0/1|null,"c4":0/1}
  • 보상 해킹 완화: c2 시각 근거를 <think> 에서 채점한다. 이 항목은 운으로 맞힌 답과 교차 추론으로 맞힌 답을 구분한다. 환각 Pitfall(c4)과 형식 게이팅(4.3)을 더한다.

4.3 견고성

  • 타임아웃, 호출 실패, 파싱 불가이면 0.0 을 반환한다(학습 중단 방지). 점수 변동을 줄이도록 심판 temperature 는 0 이다.
  • 형식 게이팅은 1부 설계 결정의 형식 게이트와 같다.

8. 검증 계획

  • 단위: 샘플 답변군(정답/오답/빈답/장황답)을 심판에 넣고 점수 단조성(정답 > 오답 > 빈답)을 확인한다. 결과: 1부 유닛테스트 29/29.
  • 분포: 변환 데이터 100~200건의 심판 점수 히스토그램으로 붕괴 여부를 본다. 결과: 8-결과.
  • 보상 해킹 프로브: 형식만 맞고 내용이 틀린 답에 심판이 낮은 점수를 주는지 확인한다. 결과: 8-결과의 오답 응답(형식은 맞음) 평균 0.00.
  • 속도: step 당 심판 지연을 잰다. 병목이면 더 작은 심판 모델, 병렬 호출, 배치 크기를 조정한다. 실측 step 시간은 00_overview 에 있다.

10. 리스크

  • 심판 비용과 속도가 학습 처리량을 낮춘다.
  • 보상 붕괴, 심판 편향·환각(임상 오판): 성능이 높은 심판, 참조답 기준 채점, 다차원 루브릭으로 완화한다.
  • 심판 자기일관성 부족: temperature 0 으로 변동을 줄인다. 외부 API 는 temperature 0 에서도 결정적이라는 보장이 없다.
