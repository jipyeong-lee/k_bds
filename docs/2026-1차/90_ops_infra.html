kgpu 운영 함정 (2026-10-23 실측)

kgpu(api.kgpu.net)는 pod 단위로 GPU 를 빌려 쓰는 외부 서비스다.

함정결과대응
감시·반납 스크립트를 Claude 세션의 백그라운드 작업으로 실행했다.세션이 끝나면 스크립트도 끝난다. 그때 trap release EXIT 가 pod 를 반납한다. 추론 비용 측정 pod 를 결과 없이 반납했다(약 600 크레딧 손실).setsid nohup bash run_x.sh > out 2>&1 < /dev/null & disown 로 세션과 분리한다.
pod 이미지(nvidia/cuda)에 python 이 없다.venv 설치 전에 둔 python3 - <<EOF 단계가 오류 표시 없이 실패했다(모델 카드 첫 테스트).python 단계는 setup_venv.sh 뒤에 $PY 로 실행한다. 산출 파일은 [ -s 파일 ] 로 검사한다.
exec 가 스크립트 시작에 실패해도 오류 없이 빈 응답을 준다.첫 추론 비용 측정은 스크립트를 시작하지 못하고 2분 만에 pod 반납으로 끝났다.exec 응답의 "background":true 와 pod 안 run.log 생성을 확인한다. 그 뒤에 감시를 시작한다.

holdout 분리 (Stage-2 평가 누수 차단)

  1. 스크립트는 scripts/make_holdout.py 다.
  2. DeepVision 에는 카테고리 라벨이 없다. 그래서 정답 유형을 대리 기준으로 쓴다(math = 수치·수식, visual-logic(vl) = 객관식).
  3. 각 유형에서 1% 를 층화 추출한다.
  4. 출력은 deepvision_holdout.jsonl(972)과 deepvision103k_trainonly.jsonl(102,531)이다.
  5. 학습은 trainonly 로, 평가는 holdout 으로 한다.
  6. 평가 스크립트 eval_compare.py 는 math 층과 vl 층을 나눠 보고한다.

구 holdout(972)의 22% 중복 (2026-07-16 발견, 재측정 보류)

검사 (holdout 972건 대 trainonly)결과
질문 + 이미지 경로가 같은 문항0건. 분리 로직은 정상이다.
질문 + 이미지 바이트해시가 같은 문항214건 (22.0%)
그중 정답까지 같은 문항(완전 중복)214건 (정답 불일치 0)
  • 원인: DeepVision 은 질문 중복이 많다(102,531행 중 고유 82,198, 중복 20,333). 같은 그림 파일이 여러 경로에 있다. make_holdout.py 는 경로 기준으로 중복을 제거해서 이 문항을 거르지 못했다.
  • 영향: DeepVision 을 학습한 모델의 수치는 상향 편향이다(dr_grpo 0.380, GDPO 0.390, GSPO 0.290, ablation 0.18·0.165). v2 콜드스타트(0.22)는 DeepVision 자기증류 727건만 학습해 일부 편향이 있다. 기본 모델(0.15)은 DeepVision 을 학습하지 않아 편향이 없다.
  • trainonly 로 학습한 3종(dr_grpo, GDPO, GSPO)은 같은 중복 문항을 학습했다. 따라서 이 3종의 상대 비교, 순위, 판정 결론은 유효하다(GDPO 와 dr_grpo 동률, GSPO 열위).
  • 오염 데이터로 학습한 모델(DAPO, baseline 0.415)과 위 3종의 차이는 당시 서술보다 작다. 위 3종도 holdout 의 22% 를 학습했다.
  • 대응: GPU 예산을 83% 쓴 시점이라 기록만 하고 재측정을 보류했다. holdout 을 다시 만들 때는 이미지 바이트해시로 중복을 제거해야 한다.
  • Stage-2 확장 holdout(1,772)은 이 972건의 이미지 해시를 학습 데이터에서 제외해 이 문제를 해소했다(21_stage2a_design.html).

2부. 기술 레퍼런스: 환경, 모델, 학습 방식, 보상, 논문

환경: Singularity 컨테이너

  • 노드 OS 는 CentOS 7.9 / glibc 2.17 이다. 이 OS 에서는 최신 ML 패키지(특히 vLLM, xformers)를 pip·conda 로 설치할 수 없다. 그래서 공식 ms-swift 컨테이너를 쓴다.
  • 이미지는 ...modelscope:ubuntu22.04-cuda12.9.1-py312-torch2.10.0-vllm0.19.1-modelscope1.35.4-swift4.1.3 이다. Gemma 4 지원에는 swift 4.0.4 이상이 필요하다(Gemma 4 12B 는 검토 후 쓰지 않았다. 아래 기본 모델 절 참조).
  • 계산 노드(드라이버 550 = CUDA 12.4)에서 swift 4.1.3, torch 2.10+cu129, vllm 0.19.1(vllm._C 정상), transformers 5.6.2 를 검증했다.
  • CUDA 마이너 호환으로 12.9 빌드가 12.4 드라이버에서 정상 동작한다.
  • SIF 는 실행할 때마다 추출이 느리다. 그래서 sandbox(디렉터리)로 변환해 쓴다(work/images/ms-swift-413-sandbox).
  • 작성 당시 최신인 swift 4.2.3 은 CUDA 13 이 필요해 이 드라이버에서 쓸 수 없다. 대안 이미지는 swift 3.8.3 / cuda 12.6.3 과 swift 3.6.4 / cuda 12.4.0 이다.
  • PyTorch 2.6 이상의 torch.load 기본값 weights_only=True 는 체크포인트 재개용 rng_state_*.pth 를 거부한다(UnpicklingError). runc.sh 가 PYTHONPATH 앞에 넣는 scripts/pyfix/sitecustomize.py 가 이 기본값을 weights_only=False 로 되돌린다.
2026-07-27 부터 apptainer 가 고장 나서 00_common.sh 기본값이 ENV_MODE=loader 다(이전 기본값 container).
  1. 원인: 호스트에 libsubid.so.3 이 없다. 클러스터 공용 apptainer 1.4.5 는 GLIBC_2.28 을 요구한다(호스트 2.17). 로그인 노드와 계산 노드 모두에서 실행할 수 없다.
  2. 이미지는 정상이다. 재빌드는 필요 없다. 이 클러스터에서는 빌드할 수도 없다.
  3. 우회: sandbox 안의 glibc 2.35 로더로 sandbox python 을 직접 실행한다(runc.sh + bin/python shim).
  4. 우회 구현에서 함정 5개를 처리했다: sys.executable, PYTHONHOME, LD_LIBRARY_PATH 분리, CUDA_HOME 실경로, Triton 용 gcc 10.2.0.
  5. GPU 검증: torch 2.10+cu129 cuda_avail True, vllm 0.19.1, GRPO 8GPU 5 step 완주(job 72832).
  6. apptainer 가 복구되면 ENV_MODE=container 로 되돌린다. 절차: HANDOFF.md §3.

기본 모델과 ms-swift 4.x 인자

  • 기본 모델(base)은 Qwen/Qwen3.5-9B(멀티모달, MODEL_TYPE=qwen3_5)다. config 는 qwen3_5, processor 는 Qwen3VLProcessor 다.
  • 기본 모델은 HF 접근 승인이 필요 없다. work/hf_cache 에 캐시하고 HF_HUB_OFFLINE=1 로 오프라인 실행한다.
  • Gemma 4 12B 는 쓸 수 없다. 실제 model_type 은 gemma4_unified 다. 이 모델에는 transformers 5.10.dev 와 CUDA 13 이미지가 필요하다. 드라이버 550 에서는 실행할 수 없어 다운로드본을 지웠다.

학습 방식: LoRA (하드웨어 제약 대응)

  • 8gpu 노드는 A100 80GB PCIe 이고 NVLink 가 없다(실측).
  • nvidia-smi topo -m 은 모든 GPU 쌍을 PHB 로 보고한다. GPU P2P 가 막혀서 NCCL 은 SHM(호스트 RAM)으로 우회한다.
  • 그래서 멀티 GPU full fine-tuning 은 18GB gradient all-reduce 에서 병목이 생긴다. 9B 모델과 짧은 시퀀스에서도 375~660초/step 이다.
  • 이 병목은 하이퍼바이저 ACS 설정에서 온다. 사용자 권한으로는 이 설정을 바꿀 수 없다.
  • 대응으로 전 단계를 LoRA 로 학습한다. LoRA 는 adapter gradient(수십 MB)만 통신한다.
  • LoRA 속도는 GRPO 약 128초/step, SFT 약 5초/step 이다(측정 조건 기록 없음). full fine-tuning(375~660초/step)과 단순 비교하면 GRPO 는 약 3~5배, SFT 는 약 75~130배 빠르다.
  • 기본 모델 가중치를 동결하므로 DeepSpeed 없이 DDP 로 충분하다.
  • 콜드스타트 LoRA 는 swift export --merge_lora 로 병합한다. 병합본을 다음 단계의 INIT_MODEL 로 쓴다.
  • LR 기본값은 SFT LoRA 1e-4 / full 1e-5, GRPO LoRA 1e-5 / full 1e-6 이다. 환경변수 LR 로 바꾼다.

보상 설계 (Stage-2)

  • 출력 형식은 <think>간결 추론</think><answer>최종답</answer> 이다. \boxed{} 는 쓰지 않는다.
  • 내장 accuracy 는 객관식 문자("B")와 기호를 파싱하지 못한다. DeepVision 은 약 48% 가 객관식 문자 정답이라 내장 함수로는 보상의 절반을 잃는다.
  • 그래서 accuracy_mix(configs/accuracy.py)를 쓴다. 수식은 math_verify 로, 객관식 문자와 문자열은 정규화 일치로 채점한다.
  • 보상 가중치는 accuracy_mix 1.0 : format_think 0.2 : soft_overlong 0.2 다.
  • vLLM colocate 인자는 --vllm_mode colocate, --vllm_mm_processor_cache_gb 0(mm_hash AssertionError 회피), --sleep_level 1 이다.

논문별 문제와 방법 (원문 요약)

기법 계보는 GRPO(기반), DAPO·Dr.GRPO(GRPO 결함 보완), GSPO·GDPO(서로 독립인 확장), RaR(검증 불가 도메인 확장) 순이다. 발표 순서와는 다르다(RaR 2025-07, GDPO 2026-01). 아래 표는 각 논문이 직전 방법의 어떤 한계를 겨냥했는지 정리한다.

논문겨냥한 문제 (직전 방법의 한계)도입한 방법
GRPOPPO 는 정책망과 비슷한 크기의 가치망(critic)을 따로 학습한다. 메모리·연산 부담이 크고 토큰별 가치 추정이 불안정하다.critic 을 없앤다. 한 프롬프트에서 응답 여러 개(그룹)를 뽑는다. 그룹 안 보상의 상대값(평균을 빼고 std 로 나눔)을 advantage 로 쓴다. critic 이 없어 메모리가 준다. 그룹 평균은 기준값(baseline) 역할을 한다.
DAPO대규모 LLM RL 에서 엔트로피 붕괴(조기 수렴), 후반 gradient 소실, 길이 폭주·잘림 노이즈가 생긴다. 기존 최고 성능 레시피는 비공개였다.4기법을 쓴다. Clip-Higher(탐색 보존, 붕괴 억제), Dynamic Sampling(std=0 그룹 폐기 후 재샘플), Token-level PG Loss(길이 정규화 편향 제거), Overlong Shaping(초과 길이 패널티·필터).
Dr.GRPOGRPO 에는 최적화 편향이 두 개 있다. (1) 시퀀스 길이로 나누는 정규화는 응답 길이 편향을 만든다(오답이 길어진다). (2) 그룹 std 로 나누는 정규화는 난이도 편향을 만든다(문제 가중치 왜곡).두 정규화를 삭제한다. 손실은 길이 대신 상수로 정규화한다. advantage 의 std 나눗셈을 없앤다. 추정의 편향이 없어진다. 토큰 효율이 오른다. 성능은 그대로다.
GSPOGRPO·PPO 의 토큰 단위 IS(importance sampling, 중요도 샘플링) 비율은 긴 시퀀스에서 분산이 누적된다. 클립은 이 분산을 키운다. MoE 와 장문에서 학습이 불안정해진다.IS 를 시퀀스(응답) 단위로 정의한다(길이 정규화한 시퀀스 우도 비율). 클립·보상·최적화도 시퀀스 단위로 한다. 분산을 억제해서 MoE(Qwen3) 학습이 안정된다.
GDPO다중 보상을 가중합한 뒤 한 번에 정규화하면 서로 다른 보상 조합이 같은 advantage 로 뭉친다. 보상 간 상대 차이가 사라진다.결합 전에 각 보상 함수를 그룹 안에서 따로 정규화(z-score)한다. 그 뒤에 결합해서 각 보상의 상대 크기와 특성을 보존한다.
RaR (Stage-3)RLVR 은 수학·코딩처럼 검증이 명확한 도메인에 강하다. 의료·과학처럼 여러 기준으로 판단해야 하는 개방형 도메인에는 맞지 않는다.루브릭 체크리스트를 구조화 보상으로 쓴다. 심판이 기준별로 채점한다. 가중 집계해서 부분 점수 보상을 만든다. 원논문은 문항별 루브릭을 쓴다. 이 과제는 정적 통일 루브릭을 쓴다.
파이프라인 대응: Stage-2 는 Dr.GRPO 를 채택했다. 길이·난이도 편향을 없애려는 선택이었다. Stage-2 형식 점수 정체의 주 원인은 v2 초기화 데이터였다(10 v2 결함). GSPO 와 GDPO 는 holdout 을 뺀 학습 데이터(trainonly)로 한 A/B 비교로 추가 검증했다. Stage-3 는 RaR 을 쓴다. 의료 VQA 는 검증 불가 도메인이다. 채택 근거와 A/B 결과: Stage-2 통합 비교, Stage-3.
