Stage-3 · 의료 RL (RaR 루브릭 보상)

개방형 의료 VQA(medix)는 정답이 하나가 아니다. 그래서 규칙 검증을 할 수 없다. 대신 Rubric-as-a-Reward(arXiv:2507.17746)를 쓴다. judge 가 가중 다기준 체크리스트를 항목별 0/1 로 채점한다. 집계는 explicit 이다: r = Σwⱼcⱼ / Σwⱼ ∈ [0,1]. 부분점수가 생기므로 보상이 dense 하다. 상세는 2부(§4.2)에 있다.

루브릭 구성 (configs/medical_reward.py build_rubric)

의도: medix 는 단답 + 멀티모달이다. "정답 하나 맞히면 끝"이 아니다. "이미지를 실제로 보고 근거를 대며 맞혔는가"를 항목으로 나눠 채점한다. 그러면 부분점수(dense) 보상이 된다. judge LLM 이 아래 항목을 0/1 로 판정한다.

RaR 루브릭 표 (두 원본의 표를 하나로 합쳤다). 가중치는 RaR 정수 스킴(Essential 5 / Important 3 / Pitfall 4)이다. 2부 §4.2 의 "정적 4차원 루브릭" 표도 이 표다.

키 (#)항목 (한/영)유형(가중)대상판정 기준(요지)
c1 (1)정답 정확성 / Answer correctnessEssential 5<answer><answer> 가 참조답과 의미 일치(동의어·단위환산·paraphrase(환언) 허용). 참조답을 기준 문장에 직접 주입(템플릿 주입)
c2 (2)시각적 근거 / Visual groundingImportant 3<think><think> 가 이미지와 모순 없는 image-relevant 관찰을 언급하고 답을 뒷받침한다(⭐ 교차추론). 없는 구조·풍경을 지어내면 실패(엉뚱/날조 묘사 = 0)
c3 (3)정밀도·단위 / Numeric precision & unitImportant 3<answer>수치 크기 + 단위가 참조답의 ±15% 이내. 측정형 문제만 자동 추가(참조답에 숫자+단위 정규식 매치 시)
c4 (4)환각·과잉주장 없음 / No hallucination / overclaimPitfall 4전체이미지에 없는 소견, 질문 범위 밖(질문 안 한) 주장을 추가하지 않는다(긍정형 문장)

집계: r = Σwⱼ·cⱼ / Σwⱼ ∈ [0,1]. 실제 비중:

  • 비측정형(분모 12): c1 42% · c2 25% · c4 33%.
  • 측정형(분모 15): c1 33% · c2 20% · c3 20% · c4 27%.
  • → 정답성(c1)이 가장 크다. 환각 억제(c4)가 다음이다.

설계 결정:

  • 정적 통일 루브릭(문제마다 생성하지 않는다). 인스턴스식(논문 방식)과 실증 비교했다(medix 40건). 정적이 오답 기각(0.000 vs 0.118)과 환각 변별(+0.338 vs +0.021)에서 우세했다. 인스턴스식은 이미지 없이 텍스트로 생성된다. 그래서 시각근거 항목을 만들지 못한다 → 정적 채택.
  • 참조답 템플릿 주입: 단답이므로 핵심 사실 = 참조답 1개다. c1 기준에 참조답을 넣는다. 그러면 오프라인 LLM 루브릭 생성이 필요 없다(비용 0, 결정적). 오프라인 GPT 생성 파이프라인 없이 코드로 루브릭을 만든다.
  • 측정형 자동 분기(is_measurement): 정답에 의료 단위(mm/cm/HU/° 등)가 있으면 c3 를 자동 편입한다. 스펙 표현은 참조답 \d+\s*(mm|cm|...) 매치 → 기준3 포함, 아니면 제외(예: "X-ray" 문항은 1·2·4).
  • 형식 게이트(format_ok): <think> 에 실질 추론(≥15자)과 <answer> 가 있어야 judge 를 호출한다. 위반하면 judge 를 생략하고 0.0 을 준다(비용↓, reward-hacking 방지).
  • c2 완화 이력: 초판 "실제 소견 인용"("구체적이 아니면 0")은 너무 엄격했다. 점수가 항상 0 이었다. "이미지(영상)와 모순 없는 관찰"로 완화했다. 완화 후 4항목이 모두 활성화됐다. 분포 프로브에서 c2 는 good 0.94 vs halluc 0.00 이다(2부 §8-결과).
  • 데이터: medix = 단답 VQA(정답 중앙값 46자, 예 "28×27mm"·"28 x 27 mm"·"X-ray"). RaR-Medicine-20k(텍스트전용·장문, 9~12항목 인스턴스 루브릭)는 비채택하고 스키마만 차용한다: {"title","description":"<Category> Criteria: ...","weight":정수}.

상세 스펙은 2부 §4.2 이다.

구현 & judge

  • configs/medical_reward.py ClinicalJudgeReward(AsyncORM): 형식 게이트 → 멀티모달 judge(env JUDGE_BASE_URL/MODEL/API_KEY) → JSON 0/1 파싱 → 집계. 타임아웃·파싱 실패 → 0.0.
  • 사용법: 
    --reward_funcs format_think clinical_judge --external_plugins configs/accuracy.py configs/medical_reward.py --reward_weights 0.2 1.0
  • judge = KHDP deepseek-v4-1-flash-ax(2026-10-15~). JUDGE_API_KEY=$KHDP_PAT 를 pod env 로 넘긴다. KISTI 계산노드에 외부망이 없어서 kgpu 에서 실행한다(../CLAUDE.md §2.5).

검증 (전부 완료)

  • ✅ 유닛테스트 29/29 · judge 스모크(FP8 이 단일 40GB 에 적합 · 정답 1.0 > 오답 0.0) · 내부망 도달성 · 분포 프로브(good 0.96 / wrong 0.00, c2 변별 Δ0.94; 상세 2부 §8-결과).
  • ✅ GRPO 배선 end-to-end 스모크(35_stage3_smoke.slurm): 플러그인 로드, clinical_judge 해석, kwargs 도달, 보상 통합을 실증했다.
    • 🐛 실버그를 찾아 고쳤다: swift 가 images 를 str 경로가 아니라 dict {bytes,path} 로 넘긴다. _image_to_data_url 이 str/dict/PIL 을 모두 받도록 고쳤다. 고치지 않으면 시각근거 c2 가 blind 가 된다. 재검증 PASS(data_url_ok=True, clinical_judge 0.58→1.0, reward = 0.2·Format + 1.0·Clinical 로 정확히 통합).
  • RL 알고리즘: RaR 는 보상 설계일 뿐이다. 최적화는 GRPO 계열이다. Stage-3 는 scale_rewards=gdpo(GDPO)를 권고한다. judge 1.0 + format 0.2 는 스케일 차이가 큰 멀티리워드이고, 이것이 GDPO 의 타깃이다. Stage-2 A/B 에서 downside 가 없음을 확인했다(판정). dr_grpo 코어(loss_type=dr_grpo · dynamic_sample)는 유지한다.

타겟 벤치마크 (HealthBench) — 의료 성능 측정

Stage-2 홀드아웃(DeepVision)은 검증가능 정답 기준의 내부 지표다. 최종 의료 능력은 외부 의료 벤치 HealthBench(OpenAI, 2025-05, 의사 262명 · 대화 5,000건 · 루브릭 채점)로 잰다. 파이프라인(SFT→RLVR→RaR) 각 단계 모델을 동일 하니스로 재서 base 대비 개선을 추적한다.

측정 세팅(scripts/45_healthbench_smoke.slurm + run_healthbench.py, evalscope health_bench):

  • Hard 서브셋 전량 1,000건(가장 변별력이 높은 부분집합), max_tokens 8192.
  • 채점자 = 자체 Qwen3.6-27B-FP8(thinking off). 오프라인 클러스터라 GPT-4.1 을 쓸 수 없다. 데이터는 로컬 캐시(오프라인)다.
  • HB_TARGET_MODEL env 로 평가 대상을 바꾼다 → base/콜드스타트/Stage-2·3 모델을 같은 조건으로 비교한다.

⚠️ 해석 주의
  1. 채점자 ≠ GPT-4.1 → 공식 리더보드와 직접 비교할 수 없다(내부 상대비교 전용).
  2. judge 파싱 실패를 보수적으로 처리한다 → 점수는 완만한 하한이다.
  3. base 가 장황하다(최대 44K자). 그래서 일부 답이 잘렸다.
추적 계획: 통합 모델과 Stage-3(RaR) 모델을 같은 하니스로 잰다. 위 표 ②③ 행을 채운다. base 0.229 대비 단계별 개선을 정량화한다.

2부. 3단계 의료 복합 보상 (clinical_judge) 구현 스펙

대상: configs/medical_reward.py + scripts/30_medical_rl.slurm
상태: 구현·검증 완료(보상 + judge Qwen3.6-27B-FP8 분포 프로브 통과). 배선은 35_stage3_smoke.slurm 로 실증했다(1부 검증).

1. 목표 & 범위

  • judge 는 3단계(개방형 의료 RL) 전용이다. 2단계 RLVR(DeepVision)은 judge 를 쓰지 않는다. 검증가능 정답을 accuracy(math_verify, \boxed{} vs ground_truth)로 규칙 채점한다(RLVR 의 정의). judge 는 불필요하고 부적합하다.
  • 3단계 데이터 MBZUAI/medix-rl-data(자유형식 임상 QA, solution = 참조답)는 단일 정답이 없다. 그래서 exact-match/규칙 채점을 할 수 없다 → LLM-as-judge 로 임상 유효성을 평가한다.
  • 복합 보상 = 형식(rule) + 임상 유효성(judge). 계획서 요구: 보상해킹·환각 억제, 다각도 평가.
  • (참고) medix 일부 답은 측정값 등 준-검증가능이다 → 필요하면 verifiable 부분집합에 accuracy 를 병용할 수 있다(옵션).

2. 핵심 결정 — AsyncORM 로 외부 멀티모달 judge API 호출

judge 는 (나중에) 대형·멀티모달 모델을 API 로 사용할 예정이었다 → in-process 방식은 맞지 않는다.

  • ms-swift 네이티브 GenRMPlugin 은 judge 모델을 TransformersEngine 로 in-process 적재한다 → 외부 API 와 맞지 않는다. 학습 GPU 도 점유한다. → 사용하지 않는다.
  • 대신 AsyncORM 을 상속한다. 검증: GRPO 트레이너가 async ORM 을 asyncio.gather 로 병렬 호출한다. reward_kwargs 에 images/solution 등 데이터셋 컬럼이 전달된다. judge API 를 async 로 호출 → 학습 GPU 미점유.
    • 등록 orms['clinical_judge'], 사용법은 1부 구현 & judge.

4. clinical_judge 상세 (ClinicalJudgeReward(AsyncORM)) — 멀티모달 API judge

파일: configs/medical_reward.py → 끝에 orms['clinical_judge'] = ClinicalJudgeReward.

4.1 동작

  • async __call__(self, completions, **kwargs): kwargs 에서 solution(참조답), images(이미지), 질문(messages)을 꺼낸다.
  • completion 마다 멀티모달 judge API 를 호출한다(이미지 + 질문 + 참조답 + 모델 답변) → 0~1 점수 파싱 → asyncio.gather 로 병렬.
  • 클라이언트: AsyncOpenAI(base_url=$JUDGE_BASE_URL, api_key=$JUDGE_API_KEY), model=$JUDGE_MODEL. 이미지는 OpenAI 멀티모달 포맷(image_url base64)으로 보낸다. (실제로 swift 는 이미지를 dict {bytes,path} 로 넘긴다 → _image_to_data_url 수정, 1부 검증.)

4.2 루브릭 = Rubric-as-a-Reward(RaR, arXiv:2507.17746) 방식 — 확정

판정을 단일 스칼라로 하지 않는다. 가중 다기준 체크리스트(0/1)로 나눈다. judge 가 항목별 0/1 을 주고 explicit 집계한다: r = Σⱼ wⱼ·cⱼ / Σⱼ wⱼ (∈[0,1]). 부분점수가 dense 하다 → GRPO zero-std 를 완화한다(2단계 교훈).

데이터 실측 반영, 핵심 단순화(LLM 루브릭 생성 불필요), RaR-Medicine-20k 스키마 차용은 1부 루브릭 구성 · 설계 결정에 합쳤다.

정적 4차원 루브릭(가중치 = RaR 정수 스킴 Essential 5 / Important 3 / Pitfall 4): 표는 1부 RaR 루브릭 표 하나로 합쳤다(#1 정답 정확성 5 · #2 시각적 근거 3 · #3 정밀도·단위 3 · #4 환각·과잉주장 없음 4).

  • 측정형 자동 분기: 1부 설계 결정 참조(참조답 \d+\s*(mm|cm|...) 매치 → 기준3 포함).
  • judge 출력 = 파싱 가능한 JSON. temperature=0. 파싱 실패 → 0.0. 
    {"c1":0/1,"c2":0/1,"c3":0/1|null,"c4":0/1}
  • 보상해킹 완화: 시각근거를 <think> 에 부여한다(운으로 맞힌 답 vs 진짜 교차추론 구분). 환각 Pitfall 과 형식 게이팅(4.3)을 더한다.

4.3 견고성

  • 타임아웃/실패/파싱 불가 → 0.0 을 반환한다(학습 중단 방지). 결정적 채점을 위해 judge temperature=0.
  • 형식 게이팅: <think> 에 실질 추론(≥15자)과 <answer> 가 없으면 judge 호출을 생략하고 0 을 준다(비용 절감 + 형식 강제).

8. 검증 계획

  • 단위: 샘플 답변군(정답/오답/빈답/장황답)에 judge 를 적용한다 → 점수 단조성(정답 > 오답 > 빈답)을 확인한다.
  • 분포: 변환 데이터 100~200건의 judge 점수 히스토그램 → 붕괴 여부.
  • reward-hacking 프로브: 형식만 맞고 내용이 틀린 답 → 낮은 점수를 확인한다.
  • 속도: step 당 judge 지연을 잰다 → 병목이면 judge 축소/병렬/배치를 조정한다.

10. 리스크

  • judge 비용/속도 → 학습 throughput 저하.
  • reward collapse / judge 편향·환각(임상 오판) → 강력한 judge + 참조답 의존 + 다차원 루브릭으로 완화.
  • judge 자기일관성 부족 → 온도 0 / 결정적 디코딩.
