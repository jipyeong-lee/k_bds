요약
  1. KISTI K-BDS 계획서 노드는 8gpu 파티션(A100 80GB PCIe × 8, NVLink 없음)이다. 예산은 Track III 한도 5,000 노드시간이다.
  2. 2026-07-21 기준 4,164.4 / 5,000 노드시간(83.3%)을 썼다. 2026-07-22 에 k252a02 계정으로 5,000 노드시간을 새로 확보했고, 07-27 에 이관을 끝냈다.
  3. Stage-2 holdout 수치는 이미지 중복 때문에 22% 상향편향이다. 상대 비교·순위는 유효하다.
  4. 환경은 공식 ms-swift 4.1.3 Singularity 컨테이너(sandbox)다. 2026-07-27 부터 apptainer 가 고장 나서 ENV_MODE=loader 로 돈다.
  5. PCIe 환경의 all-reduce 병목 때문에 전 단계를 LoRA 로 학습한다. 기법 계보는 GRPO → DAPO/Dr.GRPO → GSPO/GDPO → RaR 이다.

홀드아웃 분리 (Stage-2 평가 누수 차단)

미해결: 홀드아웃 22% 중복 (2026-07-16 발견, 기록만 — 재측정 보류)

검사결과
홀드아웃 972건 중 (질문+이미지 경로)가 trainonly 와 같은 것0건 ← 분리 로직 자체는 정상
홀드아웃 972건 중 (질문+이미지 바이트해시)가 trainonly 와 같은 것214건 (22.0%)
↳ 그중 정답까지 같은 것(= 완전중복)214건 (정답 불일치 0)
  • 원인: DeepVision 은 질문 중복이 많다(102,531행 → 고유 82,198, 중복 20,333). 또 같은 그림이 다른 경로에 중복 저장돼 있다. make_holdout.py 는 경로 기준으로 dedup 해서 이를 걸러내지 못했다.
  • 영향: 보고된 모든 홀드아웃 수치(base 0.15 / 콜드스타트 0.22 / dr_grpo 0.380 / GDPO 0.390 / GSPO 0.290 / ablation 0.18 · 0.165)는 22% 만큼 상향편향이다. 다만 clean 3종이 같은 22%를 공유하므로 상대비교·순위·판정 결론은 유효하다(GDPO≈dr_grpo 동률, GSPO 열위). "clean vs 오염(DAPO · baseline 0.415)" 대비는 서술보다 약하다 — clean 쪽도 22% 는 외운 문제다.
  • 대응(합의): 지금은 기록만 하고 재측정을 보류한다(GPU 예산 83% 소진). 향후 홀드아웃을 재구성할 때는 이미지 바이트해시 기준 dedup 이 필수다.

환경: Singularity 컨테이너 (확정·검증 완료)

  • 노드 OS 는 CentOS 7.9 / glibc 2.17 이다 → 최신 ML 패키지(특히 vLLM·xformers)를 pip/conda 로 설치할 수 없다 → 공식 ms-swift 컨테이너를 쓴다.
  • 이미지: ...modelscope:ubuntu22.04-cuda12.9.1-py312-torch2.10.0-vllm0.19.1-modelscope1.35.4-swift4.1.3 (Gemma4 지원 = swift ≥ 4.0.4).
  • 계산노드 검증(드라이버 550 = CUDA 12.4): swift 4.1.3 / torch 2.10+cu129 / vllm 0.19.1(vllm._C OK) / transformers 5.6.2. CUDA 마이너 호환(12.9 빌드를 12.4 드라이버에서)이 정상 동작한다.
  • SIF 는 실행마다 추출이 느리다 → sandbox(디렉토리)로 변환해 쓴다(work/images/ms-swift-413-sandbox).
  • 최신 swift 4.2.3 은 CUDA 13 을 요구한다 → 이 드라이버에서는 불가. 대안 이미지: swift 3.8.3 / cuda 12.6.3, swift 3.6.4 / cuda 12.4.0.
2026-07-27 부터 apptainer 파손 → 00_common.sh 기본값이 ENV_MODE=loader(구 기본값 container).

학습 방식: LoRA (하드웨어 제약 대응)

  1. NVLink 없음(실측): 8gpu = A100 80GB PCIe. nvidia-smi topo -m 이 전부 PHB → GPU P2P 차단 → NCCL 이 SHM(호스트 RAM)으로 폴백한다.
  2. 결과: full-FT 멀티GPU 는 18GB gradient all-reduce 가 병목이다 → 9B · 짧은 시퀀스인데도 375~660초/step. 하이퍼바이저 ACS 때문에 고칠 수 없다.
  3. 대응 = 전 단계 LoRA: adapter grad(수십 MB)만 통신한다 → ~128s/step(GRPO) · ~5s/step(SFT) = ~5~75배 빠름. base 가 동결이라 DeepSpeed 없이 DDP 로 충분하다.
    • cold-start LoRA → swift export --merge_lora 로 병합 → 다음 단계 INIT_MODEL.
    • LR 기본값: SFT lora 1e-4 / full 1e-5, GRPO lora 1e-5 / full 1e-6. LR= 로 override.

GRPOPPO 는 정책망과 맞먹는 크기의 가치망(critic)을 따로 학습한다 → 메모리·연산 부담↑, 토큰별 가치추정 불안정critic 제거. 한 프롬프트에 여러 응답(그룹)을 뽑아 그룹 내 보상 상대값(평균 빼고 ÷std)을 advantage 로 쓴다 → 그룹평균이 baseline 역할, 메모리↓·안정
DAPO대규모 LLM RL 의 엔트로피 붕괴(조기수렴) · 후반 gradient 소실 · 길이 폭주/잘림 노이즈 + SOTA 레시피 비공개4기법: Clip-Higher(탐색 보존 → 붕괴 억제) · Dynamic Sampling(std=0 그룹 폐기·재샘플) · Token-level PG Loss(길이 정규화 편향 제거) · Overlong Shaping(초과길이 패널티/필터)
Dr.GRPOGRPO 의 두 최적화 편향: ① ÷시퀀스길이 → 응답 길이 편향(오답이 길어짐) ② ÷그룹std → 난이도 편향(문제 가중 왜곡)두 정규화 삭제 — 손실은 길이가 아닌 상수 정규화, advantage ÷std 제거 → unbiased 추정, 토큰효율↑ · 성능 유지
GSPOGRPO/PPO 의 토큰 단위 IS 는 긴 시퀀스에서 비율 분산이 누적되고 클립이 증폭한다 → 불안정(MoE · 장문 붕괴)IS 를 시퀀스(응답) 단위로 정의(시퀀스 우도 비율 · 길이 정규화) + 클립·보상·최적화도 시퀀스 단위 → 분산 억제, MoE 안정(Qwen3)
